# 2026-08-09 개발 일지

## 주제

게임 기획 문서 에이전트의 운영 규칙을 실제 사용 방식에 맞게 단순화했다.
행동 테스트 격리, Approval Queue의 역할과 파일명, 사람용 README, AI용 규칙
라우팅을 차례로 검토하고 중복되거나 최초 제작 단계에만 필요했던 문서를
정리했다.

이 문서는 이번 대화의 판단과 변경 과정을 보존하는 역사 기록이다. 현재 동작
규칙은 `AGENTS.md`, `docs/workflows/`, `docs/skills/`와 `.codex/agents/`를
기준으로 하며, 이 개발 일지 자체는 현재 규칙의 원본으로 사용하지 않는다.

## 오늘의 목표

1. 행동 테스트의 임시 경로가 실제 프로젝트 자료와 섞이지 않게 한다.
2. Approval Queue가 모든 승인 문서를 한눈에 보여주도록 정리한다.
3. 승인 문서 파일명만 보고도 내용을 식별할 수 있게 한다.
4. 사람에게 필요한 정보는 README를 중심으로 전달한다.
5. AI가 같은 상세 규칙을 여러 문서에서 반복해서 읽지 않도록 원본 소유권을
   통합한다.
6. 최초 제작용 문서가 현재 동작에 필요한지 확인하고 불필요하면 제거한다.
7. 작업장 검증 코드의 실제 사용 방식을 명확히 한다.

## 진행 요약

1. 행동 테스트의 `<system-temp>` 경로는 실제 작업이 아니라 합성 테스트와
   실제 프로젝트 복사본을 격리하기 위한 실행 공간임을 확인했다.
2. Approval Queue와 별도 Approval Index의 역할 차이를 검토한 뒤, 별도 색인을
   추가하지 않고 Queue 하나가 모든 상태의 개별 승인 문서를 연결하도록 했다.
3. 승인 항목을 상태별로 나누고 같은 상태 안에서는 승인 ID 생성 순서로
   정렬하도록 규칙과 검증을 맞췄다.
4. 승인 파일명을 `APPR-YYYYMMDD-NNN-<content-slug>.md`로 표준화하고 기존
   항목도 내용을 설명하는 영문 slug로 정리했다.
5. README는 사람이 자주 찾는 문서 위치를 본문에서 빠르게 보여주고 자세한
   개념과 유지보수 정보는 접을 수 있는 부록에서 설명하도록 정리했다.
6. 전문 agent, PCA, 문서 분기, GAP 창작, 시나리오, 승인 적용과 문서 소유권의
   상세 규칙을 각각 하나의 canonical owner에 모았다.
7. `docs/plan.md`, `docs/architecture.md`, `docs/checklist.md`가 현재 실행에
   필요하지 않은 최초 제작 문서임을 확인하고 완전히 삭제했다.
8. `scripts/workspace_validation.py`는 독립 CLI가 아니라 테스트가 가져다 쓰는
   내부 검증 모듈임을 확인했다. 진입점은 추가하지 않고, 전체 검증 요청에는
   `unittest` 명령을 사용하도록 `AGENTS.md`에 기록했다.
9. 최종적으로 전체 자동 테스트 68개를 통과했고, 프로젝트 보호 파일 37개의
   SHA-256 집계값이 문서 정리 전후 동일함을 확인했다.

## 1. 행동 테스트와 임시 경로

### 질의

- `tmp` 경로는 실제 작업 결과를 저장하는 곳인가.
- 행동 테스트를 위해서만 사용하는 경로라면 어떤 식으로 고쳐야 하는가.

### 확인과 결정

임시 경로는 실제 프로젝트의 정본이나 승인안을 저장하는 곳이 아니다. 에이전트
호출, 승인 경계와 결과 보고를 시험할 때 합성 자료가 실제 프로젝트에 섞이지
않도록 만드는 격리 실행 공간이다.

저장소 내부에 고정 `tmp/`를 두지 않고 운영체제의 시스템 임시 디렉터리 아래에
실행별 디렉터리를 만들도록 정리했다. 기본 동작 테스트는
`tests/fixtures/behavior/sample-game/`을 복사해 실행하고, 실제 프로젝트
구조가 꼭 필요한 경우에만 프로젝트 복사본을 시스템 임시 디렉터리에 둔다.

모든 합성 입력은 `[TEST FIXTURE: SYNTHETIC]`과
`synthetic_test_fixture` 출처를 유지한다. 테스트 전후에는 원본 불변을
확인하며 테스트 산출물을 실제 프로젝트의 Approval Queue, Decision Log,
Version History 또는 `design/`으로 승격하지 않는다.

## 2. Approval Queue와 승인 문서 구성

### 질의

- Approval Queue는 AI가 사용자에게 승인을 요청하기 위해 만든 의견인가.
- 확정 자료 검색과 Approval Queue는 어떤 관계인가.
- Queue와 Index를 따로 유지할 이유가 있는가.
- 적용되거나 거절된 항목도 Queue에서 보여야 하는가.

### 확인과 결정

Approval Queue는 AI 의견 그 자체가 아니라, AI가 만든 변경안과 신규 문서
초안을 사용자가 검토할 수 있도록 상태별로 연결하는 색인이다. 확정 자료 검색은
`design/`의 승인 적용된 canonical 문서를 대상으로 하므로, 미승인 변경안을
관리하는 Queue와 역할이 다르다.

별도 Approval Index를 만들면 문서 수가 아주 많지 않은 현재 규모에서는 같은
목록을 중복 관리하게 된다. 따라서 Queue 하나를 전체 승인 문서 색인으로
사용하고 상세 내용은 항상 개별 승인 문서가 소유하도록 했다.

Queue에는 `pending`, `approved`, `needs_reconfirmation`, `applied`, `on_hold`,
`change_requested`, `rejected`의 모든 상태를 표시한다. 각 상태 안의 항목은 승인
ID 생성 순서, 즉 오래된 항목부터 정렬한다. 상태 전환은 문서를 다른 파일에
옮기는 방식이 아니라 개별 문서의 상태와 Queue의 링크 구역을 함께 갱신하는
방식이다.

### 승인 파일명

숫자 ID만으로는 내용을 알기 어려웠기 때문에 파일명을 다음 형식으로
표준화했다.

```text
APPR-YYYYMMDD-NNN-<content-slug>.md
```

`content-slug`는 승인안의 핵심 내용을 설명하는 소문자 영문 kebab-case다.
기존 승인 문서도 `visual-novel-ui-mockup`,
`project-workspace-separation`, `prologue-scenes-2a-to-4-script`처럼 제목을
식별할 수 있는 이름으로 정리했다. Queue 링크, Decision Log와 Version
History의 참조도 새 경로와 일치시켰다.

검증기에는 Queue에 없는 개별 승인 문서, Queue와 개별 문서의 상태 불일치,
상태 내부 정렬 오류, 내용 slug가 없는 파일명을 실패로 판정하는 검사를
유지했다.

## 3. 사람용 정보 전달과 README

### 방향

사람에게 현재 사용법을 전달하는 진입점은 루트 `README.md` 하나로 정했다.
README 본문에는 사용자가 자주 확인하는 프로젝트 문서의 위치와 기본 작업
흐름을 짧게 두고, 상세 개념과 내부 유지보수 정보는 하단의 접을 수 있는 부록에
배치했다.

본문에서 빠르게 찾을 수 있게 한 대상은 Project Brief, 확정 Design Index,
Temporary Ideas, Approval Queue, Decision Log와 Version History다. 부록에는
승인 상태, PCA와 전문 agent, CP·CW·NR·TBD, 출처 재확인, 에셋 승격, 문서
재구성, 폴더 지도와 자동 검증을 설명한다.

AI의 상세 행동 규칙을 README에 복제하지 않고, README는 사람용 설명과 실제
규칙 문서 링크만 제공하도록 경계를 유지했다.

## 4. AI 규칙 중복 제거

### 문제

같은 Task Packet, PCA 차단, read-only 경계, 시나리오 검수와 승인 적용 규칙이
AGENTS, workflow, skill과 전문 agent TOML에 반복되어 있었다. 문장을 반복해
읽는 비용뿐 아니라 한 곳만 수정됐을 때 규칙이 서로 달라질 위험이 있었다.

### 정리 순서와 canonical owner

1. `specialist_agent_handoff.md`가 Task Packet, provenance, PCA 확인,
   read-only, 차단 상태와 소스 제한의 공통 상세 계약을 소유하게 했다.
   다섯 전문 agent TOML에는 공통 계약 참조와 역할별 책임만 남겼다.
2. `project_creative_agent_setup.md`가 PCA 필요 여부, 생성·개정·archive,
   과거 결과와 무결성 정책을 소유하게 했다. AGENTS와 소비 workflow에는
   트리거와 링크만 유지했다.
3. `AGENTS.md`는 절대 안전 규칙과 요청 유형별 라우팅 중심으로 줄였다.
   `intake.md`의 중복 분류를 제거하고 `document_change.md`는 프로젝트·문서
   역할 판정과 branch 선택만 담당하게 했다.
4. `document_completion.md`는 GAP 발견과
   `creative_fillable | user_fact | dependency` 분류만 소유하게 했다.
   `design_creative_completion.md`는 창작 허가, 대안 생성, 선택 반영, CP와
   검수만 소유하게 했다.
5. `scenario_review.md`는 일반 시나리오 작성·검수·개선안 선택을,
   `write_ingame_script.md`는 Writer's Brief, 대본 작성, CW·NR과 독립 검수를
   소유하게 했다. `scenario_writing.md`에는 문장과 Scene 품질 기준만 남겼다.
6. `approval_queue.md`는 상태 전환, 적용 직전 원본 재확인, 결정·버전 기록과
   에셋 승격을 소유하게 했다. `document_structure.md`는 canonical owner와
   역할별 경로, 재구성 원칙을 소유하고 template은 출력 필드와 형식만
   소유하게 했다.
7. 테스트가 각 canonical owner의 필수 계약, 소비 문서의 참조, 라우터의 하위
   상세 절차 비소유와 여러 AI 지침 파일의 동일 장문 중복을 검사하게 했다.

중복 제거는 상세 원본을 한 번만 두는 구조적 정리다. 같은 파일을 한 작업에서
두 번 열지 않도록 강제하는 별도 캐시나 실행 추적 장치는 복잡도에 비해 이득이
작다고 판단해 추가하지 않았다.

체크리스트에는 완료되지 않은 항목 82개가 남아 있었지만 별도 backlog로
이관하지 않고 폐기하기로 결정했다. 제외 범위, 초기 설계 과정과 상세 검증
시나리오도 README나 새 문서로 옮기지 않았다.

### 적용

세 파일을 stub이나 archive 사본 없이 완전히 삭제했다. `AGENTS.md`의 현재
규칙 원본에서는 plan과 architecture를 제거하고 `AGENTS.md`,
`docs/workflows/`, `docs/skills/`만 남겼다. `docs/templates/`는 출력 형식만
정의한다고 명시했다. README 부록의 Workspace Architecture와 Maintenance
Checklist 링크도 제거했다.

과거 승인안과 개발 기록은 당시 판단의 증거이므로 수정하지 않았다. 따라서
`APPR-20260715-004`의 `docs/architecture.md` 근거 표기는 현재 열리지 않는
역사적 경로로 남아 있다. 기존 `docs/dev-log/`에 적힌 세 문서의 경로도 같은
이유로 보존했다.

## 6. 작업장 검증 코드의 실행 방식

### 발견한 점

`scripts/workspace_validation.py`에는 프로젝트 레지스트리, 필수 구조, 로컬
링크, 승인 기록, 적용 승인 참조, PCA와 AI 규칙 중복을 검사하는 함수가 있지만
`main()`과 `if __name__ == "__main__"` 진입점은 없다. 따라서 파일을 직접
실행하면 함수를 정의한 뒤 아무 검사 없이 종료 코드 0으로 끝난다.

이 구조는 검증 함수가 고장 난 것이 아니라 `tests/test_workspace_validation.py`가
함수들을 import하고 `unittest`가 호출하도록 처음부터 구성됐기 때문이다.
사람이나 AI가 사용하는 실제 검증 명령은 다음과 같다.

```bash
python -m unittest discover -s tests -v
```

### 최종 결정

검증은 매 파일 수정마다 실행하는 상시 게이트가 아니라, 사용자가 전체 작업장
검증을 요청하거나 에이전트가 전체 상태 확인이 필요하다고 판단했을 때 수행하는
수동 점검으로 유지했다.

독립 CLI 진입점은 추가하지 않았다. 대신 `AGENTS.md`의 `Workspace Validation`
절에 올바른 `unittest` 명령을 기록하고 `scripts/workspace_validation.py`를
직접 실행하지 않도록 명시했다. 개별 문서를 수정할 때마다 전체 검증을 자동으로
실행하지 않는다는 경계도 함께 기록했다.

## 8. 변경 경계

- 프로젝트의 승인 적용된 `design/` 정본은 수정하지 않았다.
- 기존 승인안의 내용과 상태, Decision Log와 Version History는 문서명 참조
