# TBD Tracking Workflow

## Purpose

프로젝트의 미결정 사항을 사람이 한곳에서 확인하고 답할 수 있도록
`workspace/projects/<project_slug>/tbd_tracker.md`를 관리한다. 이 문서는 수집,
입력 보존과 동기화의 상세 원본이다. 추적 문서는 보조 작업 문서이며 게임
사실, GAP 분류 또는 승인 상태의 원본이 아니다.

## Scope And Sources

1. `project_workspace.md`로 프로젝트를 확정한다. 여러 프로젝트를 명시한
   요청은 각 루트 안에서 독립적으로 처리한다.
2. Project Brief와 상태가 `confirmed`인 기획 문서의 실제 미결정 TBD를 읽는다.
   README·개요의 탐색용 요약은 상세 owner와 대조하고 중복 입력을 만들지 않는다.
   개요 자체의 미결정 사항은 수집하되 다른 문서의 항목을 대체하지 않는다.
3. Approval Queue를 통해 `pending`, `approved`, `on_hold`, `change_requested`,
   `needs_reconfirmation` 항목을 찾고 개별 Metadata 상태를 확인한다. 최신
   Draft와 현재 미해결 사항만 수집한다. 최신 범위가 불명확하면 추정하지 않고
   확인 필요로 기록한다.
4. `applied`·`rejected` 승인안, 과거 Draft, 결정·버전·개발 기록, 임시 아이디어,
   창작 규칙, 테스트 자료와 추적 문서 자체는 수집 원본에서 제외한다. 적용된
   승인안은 현재 TBD의 기존 GAP ID·관련 승인 근거를 연결할 때만 참조한다.
5. 일반적인 TBD 처리 지침, 예시와 섹션 제목만으로는 항목을 만들지 않는다.
   명시적 TBD/Open Questions 구역에 있는 미결정 질문은 본문에 TBD 문자열이
   없더라도 포함한다. 새로운 누락이나 GAP 유형은 이 작업에서 추론하지 않는다.

## Create And Collect

- `docs/templates/tbd_tracking.md`로 파일을 만들고 프로젝트 ID·확인 날짜·실제
  확인 범위를 기록한다. 첫 생성은 전체 수집 범위를 확인한다. 내용이 없으면
  구역을 지우지 않고 `항목 없음`으로 표시한다.
- 현재 기획, 미적용 승인안, 종료 항목을 나누고 원본 문서별로 묶는다. 원본은
  상대 링크로 연결하며 절 계층, Scene·항목명, 표의 행 식별자와 열을 기록한다.
  줄 번호는 확인 당시의 보조 위치이며 유일한 식별 기준으로 쓰지 않는다.
- 각 행에 ID, 원문 요약, 답할 질문, 빈 사용자 입력란, 추적 상태와 관련 승인·
  기존 GAP ID를 둔다. 질문은 원본의 빈칸을 답할 수 있게 바꾸는 데 한정한다.
- 프로젝트별 `TBD-001`부터 발급하고 최대 발급 번호 다음을 사용한다. 순서를
  바꾸거나 종료해도 ID를 재번호화·재사용하지 않는다.
- 같은 문서의 같은 결정·대상 필드가 반복되면 하나로 묶고 모든 위치를 남긴다.
  상위 요약이 여러 항목을 포괄하면 각 상세 항목에 요약 위치를 함께 기록한다.
  서로 다른 문서·승인안은 별도 ID로 유지하고 명확한 관련 항목만 연결한다.
- 긴 답변은 같은 문서의 `상세 입력`에 ID별 제목으로 적고 표의 입력란에서
  연결한다. 외부 사실·선행 결정에 대한 답에는 사용자가 근거도 적을 수 있다.

## Input And State

| 추적 상태 | 의미와 처리 |
|---|---|
| 미작성 | 아직 사용자 답변이 없음 |
| 입력됨 | 답변이 있으며 원본 반영을 위한 검토·제안이 필요함 |
| 확인 필요 | 원본 변경·충돌·부분 답변·대응 관계 불명확으로 재확인이 필요함 |
| 반영 완료 | 원본의 해당 결정 반영을 확인하고 적용 근거·날짜를 기록함 |
| 대상 종료 | 원본 삭제·제안 거부·대체 등으로 더 이상 입력 대상이 아님; 이유와 후속 항목 기록 |

사용자 입력·분류와 승인 상태는 다르다. 답변 입력만으로 승인안을 승인하거나
기획에 적용하지 않는다. 원본 변경 요청은 `document_change.md`로 넘기고
작성·검수와 `approval_queue.md`의 승인·적용 절차를 따른다. 기존 GAP ID와 유형은
출처에서만 가져오며 추적 문서 생성에 전문 agent를 호출하지 않는다.

## Synchronization

1. Project Brief·수집 대상 문서 변경, 승인안 등록·개정·상태 변경·적용 뒤 메인
   Codex가 해당 프로젝트의 영향받는 항목을 갱신한다. 외부 편집은 다음 관련
   작업이나 사용자 갱신 요청 때 감지한다. 상시 감시 프로그램은 사용하지 않는다.
2. 갱신 직전에 추적 문서와 원본을 다시 읽는다. ID·사용자 답변·상세 입력·관련
   승인·종료 기록을 보존하며 전체 재생성으로 덮어쓰지 않는다.
3. 변경 없는 항목은 유지하고 신규 항목만 추가한다. 위치 이동만 명확하면
   locator를 갱신한다. 의미·범위가 바뀌거나 대응이 불명확하면 이전 요약과
   답변을 보존하고 변경 이유·현재 원본을 적어 `확인 필요`로 둔다.
4. TBD 문자열이 사라졌다는 사실만으로 완료하지 않는다. 적용된 결정과 현재
   원본의 일치를 확인해야 `반영 완료`로 옮긴다. 원본 삭제·거부·대체는
   `대상 종료` 사유와 날짜를 남긴다. 증거가 부족하면 `확인 필요`다.
5. 승인안 적용 후에도 정본에 TBD가 남으면 기존 정본 항목에 연결하거나 새
   정본 항목을 만들고 승인안 항목은 그 ID를 연결해 `대상 종료`로 보존한다.
   초안과 정본의 입력을 자동 병합하지 않는다. 종료 원본이 삭제되면 깨진 링크
   대신 당시 경로를 텍스트로 남기고 살아 있는 후속 문서를 연결한다.
6. 마지막 확인 날짜와 실제 확인한 문서 범위를 기록한다. 부분 갱신은 전체
   재검사로 표시하지 않는다. 최초 전체 확인 날짜도 유지한다.

## Verification

- 대상 원본의 TBD 검색 결과와 명시적 미결정 질문을 대조하고 누락·제외 이유,
  반복 위치, 표의 서로 다른 빈칸을 확인한다.
- 링크의 존재, 프로젝트 경계, ID 중복과 사용자 입력 보존을 확인한다.
- 추적 문서·README 작업 링크 관리는 확정 기획 변경이 아니며 자체 승인안이나
  Decision Log·Version History 기록을 만들지 않는다.
